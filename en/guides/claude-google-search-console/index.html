How to connect Claude to Google Search Console

To The Sky · 26 November 2026

You can connect Claude to Google Search Console through a third-party MCP server that uses Google's public API. In our setup, we use mcp-search-console with OAuth, read-only by default. Below are the steps we followed in Claude Code, the prompts we use, and the problems we encountered.

Choose your access method and where the server runs

What you can do after connecting

Connecting lets you ask for Search Console data directly in Claude. You can list properties, review search performance, compare periods, and inspect URLs. For marketers, SEO people, and business owners, the practical value is simple: you can start with a question and ask for the data relevant to it.

At To The Sky, we are a young, dynamic team based in Malta, working on ads and websites. We use this connection to investigate organic search questions. We do not need to publish our own site's traffic figures to explain the workflow.

Based on our checks in November 2026, Google publishes official MCP servers for Google Analytics, but we did not find an official Google MCP server for Search Console. Every Search Console MCP server we found is third-party code that calls Google's public Search Console API.

We use mcp-search-console, an open-source server with an MIT license. It is read-only by default. Actions that change things require GSC_ALLOW_DESTRUCTIVE=true. We keep it read-only.

If you also work with Analytics data, see our Claude and Google Analytics 4 guide. Treat that as a separate connection. The steps below focus specifically on Search Console. For the full picture, read our guide to Claude for marketing.

What you need before you start

Start with the Google account that owns the Search Console properties you want to analyse. Our connection instructions use Claude Code, so you need that for the command shown later. The server runs with uvx, which comes from uv. Have those pieces ready before you add the connection.

You also need a private place for the OAuth client JSON file and the saved token. Choose that location before downloading the file. Do not use a shared folder, a Git repository, or notes. These files give read access to your Search Console data.

Decide where the MCP server will run. For one person, running it locally on a laptop is enough. We run it on our own small server so our Claude chats and team use one shared copy. That is our setup, not a requirement for getting started.

Prepare the information for your Google app as well: an app name, support email, contact email, home page, privacy policy link, and domain. You will enter these in Google Auth Platform.

If your setup also involves Tag Manager, keep our Claude and Google Tag Manager guide separate. Here, keep the Google Cloud project focused on the Search Console connection.

Choose OAuth or a service account

You have two ways to give the server access. The choice depends on which properties you want available and how you prefer to grant access. Neither option is automatically the right fit for everyone.

With OAuth, you sign in using your own Google account. Claude sees every Search Console property that account can see. This is useful when you already work across several sites through the same account and want them available through the connection.

With a service account, you must add its email as a user in Search Console on each property. Creating the service account does not replace that step. You need to grant access wherever you want to use it.

We first tried the service account route. We then switched to OAuth because we wanted all the sites in our account without adding a user on every property. That was the practical reason for our choice, not a claim that OAuth is always better.

Keep the account-wide access in mind when choosing OAuth. Before asking for reports, request the property list and permission levels. A property appearing in that list does not mean every data request will work. We encountered that distinction in our own setup.

Create the Google Cloud project and enable the API

Begin the setup in Google Cloud. We created a separate project used only for this connection. The reason was straightforward: we did not want this setup to touch projects used for other tools. Follow the same approach if you want to reproduce our setup.

1. Create a separate Google Cloud project for the connection between Claude and Search Console. 2. Enable the Google Search Console API in that project.

Those are the steps needed at this stage. Keep the next part of the OAuth setup in the project dedicated to this connection. Later, you will create the Desktop app client there and save the JSON file that the MCP server uses.

Enabling the API is one part of the setup. You still need to configure the app, create the OAuth client, and sign in with the correct Google account. Do not stop after enabling the API and assume Claude already has access to your properties.

This separation also helps when you work with other Claude connections. For example, our Claude and Google Ads guide covers another part of your marketing work. For this guide, stay focused on the Search Console project and its API.

Next, define the app you will sign in through. Its audience and publishing status matter for the login.

Configure the app and create the Desktop client

After enabling the API, continue in Google Auth Platform. This is where you configure the app used for the OAuth login. Use the information you prepared earlier, and keep the resulting client file private.

1. Enter the app name and support email. 2. Set the audience to External and enter the contact email. 3. Add the home page, privacy policy link, and your domain as an authorized domain. 4. Publish the app to production. 5. Create an OAuth client of type Desktop app and save the JSON file somewhere private.

Publishing matters for keeping the login working. Google's documentation says that while an External app is in Testing, refresh tokens expire after 7 days. Leaving it in that state would mean the login stops working every week. That is why we published our app to production.

Publishing an unverified app works for a small number of users. During login, Google shows a "Google hasn't verified this app" screen. In our case, this is our own app created for this connection, so we choose Advanced and continue. Do not treat that choice as general advice for unfamiliar apps.

Save the JSON in a private secrets folder with restricted permissions. Keep it out of shared folders, repositories, and notes. The command in the next section will point to its location.

Add the server to Claude Code and sign in

With the Desktop client JSON saved securely, you can add the MCP server to Claude Code. Replace the placeholder path with the path to your private file. Keep the file on the machine running your setup; do not copy its contents into a conversation.

1. Add the server with this command:

claude mcp add search-console -s user -e GSC_OAUTH_CLIENT_SECRETS_FILE=/path/to/client_secrets.json -- uvx mcp-search-console

2. Sign in once in the browser with the Google account that owns the Search Console properties. 3. Allow read access using the webmasters.readonly scope. 4. Restart Claude and ask: "List my Search Console properties."

The server saves a token and refreshes it on its own. GSC_CONFIG_DIR sets where that token is stored. Give that location the same protection as the client JSON: private storage with restricted permissions, and no copies in chats, documents, or repositories.

If you need a new login, the server also includes reauthenticate. Keep the setup read-only. You do not need actions that change things to ask for performance reports, compare periods, or inspect URLs.

Your first response should help you identify the property you want to work with. Ask for permission levels before requesting data. In our setup, the correct property and its permissions mattered more than simply seeing the site listed.

Use prompts that start with a clear question

Start with the property and permissions, then move to performance. These are the prompts we use to move from an overview to questions about pages and queries. Use them individually, depending on what you want to investigate.

"List my Search Console properties and their permission level."

"Show clicks, impressions, CTR and position for the last 28 days, compared with the previous 28 days."

"Which queries have impressions and an average position between 8 and 20? Group them by page."

"Which pages lost the most clicks compared with the previous period?"

"Inspect these new URLs and tell me which are indexed and which are not."

"Which URLs still get impressions but should redirect to a new page?"

The server tools we use are list_properties, get_performance_overview, get_search_analytics, compare_search_periods, get_search_by_page_query, inspect_url_enhanced, batch_url_inspection, and get_sitemaps. The prompts let you express the practical question without putting all those tool names into every request.

Treat the result as a starting point for investigation. A drop in clicks or an old URL still receiving impressions tells you what to check next. It does not, by itself, establish the cause. If that investigation leads to website work, you can review our website service.

Check permissions, reporting periods, and private files

Our first real problem was property permissions. Our account showed both a URL-prefix property and a Domain property for our site. The Domain property, identified by sc-domain:, appeared with "unverified user" permission. Requests returned a 403 "User does not have sufficient permission" error. The URL-prefix property where we are owner worked.

Check the permission level in the list before requesting data. If you see the same problem, do not assume the entire connection is broken. In our case, the difference was between the properties and the permissions available for each.

Another trap concerns recent data. The latest days can be incomplete in Search Console. Compare full periods, and keep this in mind when using the prompt about the last 28 days.

In the page report, we also found an old URL from before our site restructure still getting impressions. That told us to check redirects. It was a reason to investigate, not proof of a particular cause.

Finally, protect both the client JSON and the token. Keep them in a private secrets folder with restricted permissions. Never paste them into chats, documents, or repositories. If a file leaks, delete the OAuth client in Google Cloud and create a new one. Keep the server read-only; we do not enable adding or deleting sites or managing sitemaps.

How we made this guide: we started from our own work, in the accounts we manage and the tools we use. An AI assistant helped us with the draft and structure. Before publishing, we checked every figure, step and link against our own data and setup.

In short

To connect Claude to Google Search Console, our setup uses a separate Google Cloud project, a Desktop OAuth client, and the third-party mcp-search-console server, read-only by default. After signing in, check property permissions, compare full periods, and keep the client JSON and token private.
