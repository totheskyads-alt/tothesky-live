Our Claude stack for marketing

What Claude for marketing really means

Most people meet Claude in a chat window. You paste a table, ask a question and get an answer. That is useful, but it is not where the real time savings are in marketing. The real work happens inside your tools: the ad accounts, the analytics property, the tag container, the session recordings and Search Console. Copying data out of each one by hand is slow, and the numbers are old by the time you paste them.

The Model Context Protocol, MCP for short, solves this. It is an open standard that lets Claude connect to outside tools through connectors, also called MCP servers. Once a connector is in place, you ask your question in plain language and Claude reads the data straight from the tool. Some connectors are official and come from the tool's maker. Others are open-source or built by third parties on top of a public API.

We set our connectors up in Claude Code, in the terminal or in the Code tab of the Claude desktop app. That is the environment all our guides use.

So when we say Claude for marketing, we mean three things working together. First, Claude can read your marketing data where it lives. Second, it can combine sources in one answer, for example what GA4 shows next to what Google Ads reports. Third, it can prepare work for you: a paused ad draft, a draft tag workspace, a plan for a campaign change. A person still reviews that work and decides what goes live.

This page is the map of how we do it at To The Sky. Each tool has its own detailed guide with the exact steps, and we link to every one of them below. If you only want one tool, jump straight to its guide. If you want the full picture, read on.

What you need before you start

You do not need to be a developer, but a few things make the setup smooth.

1. Claude Code, either in the terminal or in the Code tab of the Claude desktop app. 2. Access to the tools you want to connect, with the right role. For reading, a viewer or read role is usually enough. For changes you need more, and you should think about who really needs that. 3. For the Google tools, a Google Cloud project where you enable the right API and create the access Google asks for. We use a separate project for each connector. 4. A private place for keys, client files and tokens. On our machines that is a secrets folder with restricted permissions, never a shared drive. 5. One clear first question for each tool, so you can test the connection with something you already know the answer to.

The last point matters more than it looks. When a connection works, the first answer always looks impressive. The way to know it is correct is to ask something you can check by hand, then compare. In the GA4 guide our first test is simply to list the accounts and properties. In the Search Console guide it is the list of properties with their permission level.

Set aside some quiet time for each tool. The Google tools take longest, because of the Cloud project, the API and the sign-in. The Microsoft Clarity connector is quicker: you create a project token and add the connector, as we show in the Clarity guide.

Finally, decide early where the connectors will run. For one person, running them locally on the laptop is enough. We run ours on our own small server, so every Claude chat and the whole team share one copy instead of each chat starting its own.

The stack we use, tool by tool

Here is what we connect and why. Each line links to the full guide.

For Meta, we use Meta's official Ads MCP server, added as a custom connector, with sign-in through Meta. We use it to analyse client accounts and to prepare paused ad drafts for review. The steps are in our Claude and Meta Ads guide.

For Google Ads, Google's official connector covers reporting and supported asset operations. For campaign changes we use an open-source connector with write access, hosted on our own server, with a required dry run, a budget cap and a person who approves each proposal. See the Claude and Google Ads guide.

For analytics, we use Google Analytics MCP, Google's official connector, which is read-only. We ask about channels, funnels and conversions, always on complete days. The setup is in the Claude and GA4 guide.

For tracking, a GTM MCP server builds tags and triggers in a draft workspace, and Chrome DevTools MCP checks what actually fires on the site. A person reviews and publishes. Details in the Claude and Google Tag Manager guide.

For behaviour, we use Microsoft's official Clarity connector to review Clarity data and choose which recordings are worth watching, for example mobile sessions with rage clicks. See the Claude and Microsoft Clarity guide.

For SEO, we did not find an official Google MCP server for Search Console, so we use the open-source mcp-search-console with OAuth on a separate Google Cloud project. It is read-only by default. The full setup, including a permission trap we hit, is in the Claude and Google Search Console guide.

You do not need all six on day one. Most teams get the most value from one ad platform plus GA4, then add the rest as questions come up.

Start read-only, then add changes through drafts

The safest way to start is the same for every tool: read first, change later.

1. Connect the tool with read access. 2. Ask Claude to list what it can see: accounts, properties, containers or sites. 3. Ask one clear question you can check by hand. 4. Compare one number with the tool's own interface. 5. Only then decide whether this tool needs anything more than reading.

For many tools the answer is no. GA4, Clarity and Search Console give us most of their value through reading. We ask questions, Claude finds the pattern, and we decide what to do on the site or in the campaigns.

Where changes do make sense, we never let them go straight to live. Every change goes through a draft. On Meta, Claude prepares ads that stay paused until a person activates them, as described in the Meta Ads guide. In Tag Manager, Claude works in a new draft workspace and reports what it built, and a person reviews and publishes, as shown in the Tag Manager guide. On Google Ads, the connector we use for changes requires a dry run first, works under a budget cap and needs a designated person to approve each proposal, as explained in the Google Ads guide.

This rhythm, read, propose, approve, apply, is what makes the setup safe enough for client accounts. It also keeps the work reviewable. When something looks off, you can see exactly what Claude proposed and what a person approved.

It also changes how you write prompts. Instead of "fix the campaign", you ask for an analysis, then a proposal, then the change as a draft. Each step is small and easy to check.

Ads: Meta and Google

Ad accounts are where Claude saves us the most routine time, and where the rules matter most, because money moves.

On Meta, the official Ads MCP server lets Claude read the account and prepare new ads. We use it in two ways. First, analysis: which campaigns, ad sets and ads are carrying the results, and which are spending without much to show. Second, preparation: when we want to test a new angle, Claude prepares the ads as paused drafts. A person looks at them, changes what needs changing and activates them. Meta's own controls, like budgets and spending limits, stay in place as a second safety net. The full walkthrough is in our Claude and Meta Ads guide.

On Google Ads, the choice of connector depends on what you need. If you only need reporting and supported asset operations, Google's official connector is enough. We also make campaign changes, so we use an open-source connector with write access on our own server. It never applies a change directly. It prepares a plan, shows a dry run, works under a budget cap and waits for a designated person to approve. The Claude and Google Ads guide walks through both options.

A few habits keep ad work clean:

1. Always name the account you mean. Agencies see many accounts with similar names. 2. Ask for the period explicitly, and prefer complete days. 3. Ask Claude to explain its reasoning before it proposes a change. 4. Keep one person responsible for approvals on each account.

If you work with a team or an agency, these habits also make handovers easier, because every change has a written proposal behind it. For hands-on help with campaigns, see our Google Ads and Facebook and Instagram services.

Measurement: GA4, Tag Manager and Clarity

Good ads depend on good measurement. Here Claude helps mostly by checking.

With GA4 connected through Google's official Google Analytics MCP, we ask questions we would otherwise answer by building reports by hand. Which channel brings new buyers? Where do people drop out of the funnel? How does what GA4 shows compare with what Google Ads reports? The connector is read-only, which suits the job. We always ask about complete days, and before acting on an answer we check one number by hand. The setup is in the Claude and GA4 guide.

Tag Manager is where tracking gets built, and it is easy to break. We tell Claude which conversion we want to track. Through the GTM MCP server it builds the tags and triggers in a new draft workspace. Then, through Chrome DevTools MCP, it opens the site and checks what actually fires, for example on the thank-you page after a purchase. We read its report and publish only when the result is right. The full process is in the Claude and Google Tag Manager guide.

Microsoft Clarity answers a different question: what do people actually do on the page? Through Microsoft's official connector, Claude reviews the Clarity data and tells us which recordings are worth watching. A typical first question is about mobile sessions with rage clicks. Instead of watching hours of recordings, we watch the few that explain the problem. One practical note: for data older than the last 1 to 3 days, we use the Clarity dashboard. Details are in the Claude and Microsoft Clarity guide.

Together, these three give you a loop. GA4 tells you where something goes wrong, Clarity shows you why, and Tag Manager makes sure the fix is measured correctly.

SEO with Search Console

Search Console holds the data that matters most for organic traffic: which queries show your pages, how often people click and where you rank. Connecting it to Claude turns that data into answers you can act on quickly.

When we set it up, we did not find an official Google MCP server for Search Console. Every option we found was third-party code calling Google's public Search Console API. We chose the open-source mcp-search-console, with OAuth on a separate Google Cloud project, so Claude sees the properties our account can see. It is read-only by default. The full setup is in the Claude and Google Search Console guide.

What we ask most often:

1. Clicks, impressions, CTR and position for the last 28 days, compared with the previous 28 days. 2. Queries that already get impressions with an average position between 8 and 20, grouped by page. Those pages are close to the first page and usually the quickest wins. 3. Pages that lost the most clicks compared with the previous period. 4. Whether a list of new URLs is indexed. 5. Old URLs that still get impressions and should redirect to a new page.

That last one came from real use. In our own page report we saw an old address from before a site restructure still getting impressions. It told us to check our redirects.

Two traps to know. First, a Domain property can show up with an unverified user permission and return a 403 error, while the URL-prefix property for the same site works. Check the permission level before you ask for data. Second, the latest days in Search Console can be incomplete, so compare full periods.

Search Console also pairs well with Clarity: once you know which page ranks but does not convert, you can ask which recordings on that page are worth watching.

The prompts we use every week

The connectors are only as useful as the questions you ask. These are prompts we actually use. Each one starts with a clear question and asks for something you can check.

For analytics, from the GA4 guide:

"List my GA4 accounts and properties."

"Which channel brings new buyers in the last 90 days?"

For SEO, from the Search Console guide:

"Show clicks, impressions, CTR and position for the last 28 days, compared with the previous 28 days."

"Which queries have impressions and an average position between 8 and 20? Group them by page."

For behaviour, from the Clarity guide:

"Show mobile sessions with rage clicks and tell me which recordings to watch."

For tracking, from the Tag Manager guide:

"Create a new draft workspace with a purchase conversion tag and tell me what fires on the thank-you page."

For ads, from the Meta Ads guide and the Google Ads guide:

"Analyse this ad account for the last 30 days and prepare two paused ad drafts for review."

"Prepare the Google Ads change as a dry run and show me the plan before anything is applied."

Notice the pattern. Each prompt names the period, says exactly what to return and, when it involves a change, asks for a draft or a plan rather than an action. That makes the answer easy to verify and keeps a person in control.

A good habit is to keep your best prompts in one shared document and improve them over time. When a prompt gives a confusing answer, the fix is usually to make the question narrower, not to ask Claude to try harder.

Security and permissions

Connecting Claude to your marketing tools means giving software access to client accounts and data. We treat that access with the same care as a password.

Keys, client files and tokens live in a private secrets folder with restricted permissions. They never go into a chat, a shared document, a note or a code repository. If a file ever leaks, you delete the client or token in the tool and create a new one. Our Search Console guide shows this for the Google OAuth client.

We use a separate Google Cloud project for each connector. That way, a change made for one tool, a new API or a new sign-in, does not touch the projects used by the others.

We give each connector the smallest access that does the job. GA4, Clarity and Search Console are read-only by default. Meta gets reading plus paused drafts. Google Ads gets changes only through a dry run, a budget cap and an approval, as described in the Google Ads guide. Tag Manager works in draft workspaces, and a person publishes, as in the Tag Manager guide.

One rule deserves its own paragraph. Text on a web page, in an email or in a message can try to give instructions to an AI agent. A person reading the page would ignore it, but an automated agent might not. So any agent of ours that reads web pages, emails or messages on its own stays read-only. Write access is only for chats where a person asks for the work and approves it.

Finally, keep a record. When a connector can change things, the proposal, the approval and the result should all be written down somewhere you can check later.

How to start this week

You do not need a big project to get value from Claude in marketing. Here is a simple plan we would follow with a new team.

1. Pick the one tool where you spend the most time copying data by hand. For most teams that is GA4 or the main ad account. 2. Follow the guide for that tool and connect it read-only: GA4, Meta Ads or Google Ads. 3. Test the connection by listing accounts or properties, then ask one question you can check by hand. 4. Use it for a week on real questions. Write down the prompts that work. 5. Add a second tool that answers the next question you keep asking. If you want to know why a page does not convert, add Clarity. If you want organic traffic, add Search Console. If your tracking is unreliable, add Tag Manager. 6. Only when reading is routine, consider changes, always through drafts and approvals. 7. Move keys into a private secrets folder from day one, and decide who approves changes on each account.

After a few weeks you will have a small stack that answers most of your routine questions in minutes, and a set of prompts your whole team can reuse.

If you would rather have this set up and run for you, or you want a second pair of eyes on your ads and tracking, get in touch with us. We are a young, dynamic team in Malta, and this is the setup we use every day on our own and our clients' accounts.

How we made this guide: we started from our own work, in the accounts we manage and the tools we use. An AI assistant helped us with the draft and structure. Before publishing, we checked every figure, step and link against our own data and setup.

In short

Start with one tool, read-only, and one clear question you can check by hand. Add changes only through drafts, dry runs and a person who approves. Keep keys private, keep agents that read web content read-only, and let Claude do the reading and preparing while people make the decisions.
